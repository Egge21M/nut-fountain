# CDK PR #2646 versus updated NUT-16

Comparison snapshots: [CDK `b56afd3`](https://github.com/cashubtc/cdk/tree/b56afd3fe96f944966c296c79a5a394175ff498e), [NUT-16 `737bcd9`](https://github.com/Egge21M/nuts/blob/737bcd98a8ad8acd925dc62f560a985155c08471/16.md). This note records a focused compatibility investigation, not a submitted GitHub review.

## Fountain limits

CDK still caps source fragments at 256, versus 1024 in the updated NUT. Its encoder rejects messages requiring more than 256 fragments, and its frame parser rejects metadata above that count. Transfers with 257–1024 fragments therefore remain incompatible. [CDK bound](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut16/fountain.rs#L38-L45), [encoder check](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut16/fountain/codec.rs#L31-L48), [frame parser check](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut16/fountain/codec.rs#L311-L316), [updated NUT bounds](https://github.com/Egge21M/nuts/blob/737bcd98a8ad8acd925dc62f560a985155c08471/16.md#L56-L65).

Two related changes are needed when raising this limit:

1. `MAX_MESSAGE_LENGTH` currently derives from `MAX_FRAGMENT_LENGTH * MAX_FRAGMENT_COUNT`. Its present value is correctly 1 MiB; raising only the count would incorrectly raise it to 4 MiB. It must remain an independent 1 MiB limit. This is a required companion change, not an existing oversized-message acceptance bug. [CDK definition](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut16/fountain.rs#L43-L45), [independence requirement](https://github.com/Egge21M/nuts/blob/737bcd98a8ad8acd925dc62f560a985155c08471/16.md#L65).
2. `resolved_fragment_count()` stores each coefficient row in `[u64; 4]`, exactly 256 bits. Its indexing would exceed that capacity for a retained row with more than 256 coefficients after increasing the accepted count. It needs 1024 bits or dynamically sized storage, plus updated tests/docs. This is a conditional failure if the limit alone is raised; current input checks prevent it. [Fixed-size helper](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut16/fountain/codec.rs#L230-L250).

The module docs and committed compatibility tests still refer to nut-fountain `v0.1.0-alpha.0`, rather than the updated NUT-16 snapshot. [Module reference](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut16/fountain.rs#L1-L13), [compatibility test suite](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut16/fountain/tests.rs#L1-L34).

## Cashu payload and binding findings

### Existing text tokens are reserialized instead of preserving CBOR

NUT-16 requires converting an existing `cashuB` token by decoding its base64url body, preserving the original CBOR, and prepending `crawB`. [Requirement, line 41](https://github.com/Egge21M/nuts/blob/737bcd98a8ad8acd925dc62f560a985155c08471/16.md#L41).

CDK's normal `Token::from_str(text)` → `token.fountain_encoder(size)` path loses the original encoded representation: it parses CBOR into `TokenV4`, then serializes the struct again. The new fountain wrapper takes a typed token only. [Text parser](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut00/token.rs#L219-L244), [new fountain encoder](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut16/fountain.rs#L109-L122), [serialization](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut00/token.rs#L497-L503).

Concrete example from the PR itself: base64url-decoding its existing `TOKEN` fixture produces CBOR beginning `a4 61 74`, i.e. a four-entry map whose first key is `t`. CDK's derived serializer uses declared field order `m,u,d,t`. Thus this path does not preserve the bytes even for its ordinary example token. Re-encoding can change message bytes, message CRC and fountain payloads without changing the ordinary parsed token's meaning. [Fixture](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut16/fountain/tests.rs#L12), [field declaration order](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut00/token.rs#L433-L447).

The generic byte-oriented encoder remains a route for a Rust caller to transmit correctly preserved `crawB` bytes. This is a token-conversion requirement mismatch, not an incompatibility of the fountain frame algorithm. The FFI token helper follows the same typed-token conversion. [Generic encoder export](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut16/fountain.rs#L36), [FFI helper](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cdk-ffi/src/token.rs#L187-L202).

### Existing token parser exposes a witness-field incompatibility

NUT-00 V4 encodes optional witness metadata under `w`. CDK's existing `ProofV4` uses the field name `witness` without a serde rename or alias to `w`. Consequently serde ignores a standard `w` field when parsing and defaults `witness` to `None`; when a typed witness is present, serialization uses `witness` rather than `w`. The new fountain token wrapper calls this existing parser and serializer. This is an inherited token-layer problem exposed by the new API, not a newly introduced fountain-selection defect. It matters for witness-bearing Cashu tokens: successful binary reconstruction alone does not preserve that metadata in the returned typed token. [NUT-00 V4 witness field](https://github.com/Egge21M/nuts/blob/737bcd98a8ad8acd925dc62f560a985155c08471/00.md#L271), [CDK ProofV4](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut00/mod.rs#L437-L455), [token decoder wrapper](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut16/fountain.rs#L194-L202), [existing binary parser](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut00/token.rs#L247-L260).

This conclusion follows directly from the Rust serde declarations and call path. No compiled full-CDK token round-trip test was run in this focused inspection.

## Allowed API differences and scope

- `complete()` describes fountain reconstruction; `token()` performs the additional Cashu envelope parsing. This separation is explicitly documented in CDK and does not itself violate the NUT's separate fountain/Cashu completion requirements. [CDK contract](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut16/fountain.rs#L166-L171), [NUT receiver requirements](https://github.com/Egge21M/nuts/blob/737bcd98a8ad8acd925dc62f560a985155c08471/16.md#L184-L192).
- Accepting a V3 typed token and converting it to V4 before transport is an extra convenience. The emitted message still uses V4 `crawB`; this is not evidence of a wire-format mismatch. [Encoder conversion](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut16/fountain.rs#L115-L122).
- FFI forwards complete byte vectors to the canonical Rust encoder/decoder and exposes its results. There is no separate binding-specific selection algorithm. Actual QR generation, camera extraction, and segment-mode restrictions remain application work; this PR's FFI supplies raw frames. [FFI encoder/decoder](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cdk-ffi/src/types/fountain.rs#L28-L99).
- Full-length keyset IDs are not rejected merely because CDK names the storage type `ShortKeysetId`: its parser keeps a variable-length prefix. No full-keyset-ID compatibility finding is established here. [Parser](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut02.rs#L398-L407).

## Validation and limitations

Read the pinned specifications, token types and serde declarations, new fountain token API, FFI wrappers and tests. Independently base64url-decoded the existing CDK token fixture to establish the original CBOR first key. The coordinating review ran all seven committed CDK fixtures against the current local TypeScript implementation: 562 emitted frames matched byte-for-byte, and 583 decoder transitions passed. These results establish agreement for those existing fixtures; they do not execute the Rust code or establish 1024-fragment support. [Committed fixture source](https://github.com/cashubtc/cdk/blob/b56afd3fe96f944966c296c79a5a394175ff498e/crates/cashu/src/nuts/nut16/fountain/testdata/fountain.json).

Rust `cargo` and `rustc` are unavailable in this environment, so the Rust findings are based on source inspection, and no full-workspace build or generated-language binding test was run. No CDK source files or remote PR were changed.
